# 37. The reference deployment is a hand-authored Docker Compose distribution, SQLite-base with a Postgres overlay

**ZWarden ships a self-contained `deploy/compose/` distribution an operator runs with
`./bootstrap-secrets.sh && docker compose up -d`.** It wires **Caddy** (the sole front door, ADR 0035) →
**ZWarden.Web** (never host-published) → the **ZWarden.Agent** host worker, whose Docker path runs only
through the **wollomatic** socket-proxy (ADR 0008). **SQLite is the base mode** (`compose.yaml`, one persisted
volume, no database service); **PostgreSQL is an overlay** (`compose.postgres.yaml`) that adds the `postgres`
service and flips the Web service's provider + connection string (ADR 0005). Secrets live in a **git-ignored
`.env`** generated by a bootstrap script (the AES key ring of ADR 0015, the DB password); **Agent enrollment
is operator-driven through the F33 wizard**, not auto-seeded. Startup is **health-ordered** on Web's
unauthenticated `/healthz` liveness probe. Project Zomboid game-server containers are **not** Compose
services — the Agent creates them at runtime on the host daemon (F13).

- Status: accepted
- Decided in: #53 (F34 — Complete Docker Compose Distribution); mini-plan
  `docs/feature-plans/F34-complete-docker-compose-distribution.md`
- Bears on: PRD §11 criterion 1 (deploy the supported stack with minimal setup, satisfied by F32+F33+F34);
  PRD §45 (Web never Internet-exposed); PRD §24 (non-root runtimes). Builds on ADR 0031 (Aspire is dev/test
  only — F34 is the production twin of that graph, minus Aspire), ADR 0035 (Caddy ingress; its Caddyfile is
  wired in unchanged), ADR 0008 (wollomatic socket-proxy + its allowlist), ADR 0015 (fail-closed key ring),
  ADR 0005 (dual EF provider), ADR 0007 (outbound-WSS agent auth), ADR 0036 (First-Run Setup finishes
  bootstrap after the stack is up). Feeds F35 (#54, remote agents against the same control plane).

## Context

F32 shipped the Caddy ingress ingredient and F33 the first-run wizard, but there was no artifact that stood
the whole system up: no images for ZWarden.Web or ZWarden.Agent (only F12's PZServer had a Dockerfile), no
Compose file, no secrets bootstrap, no documented upgrade path. The dev/test graph exists as an Aspire AppHost
(#123, ADR 0031), but Aspire is explicitly not a production packager — production needs self-contained,
pinned, non-root images and a hand-authored Compose with real volumes, networks, health ordering, and both
supported database modes (ADR 0005: SQLite and PostgreSQL are both v1.0 deployment modes).

Three facts shaped the wiring. First, the Agent's config validator (F8) requires an `https`/`wss` control-plane
URI and fails closed otherwise, so the co-located Agent cannot connect to Web over plain HTTP on the internal
network — it must go through Caddy. Second, ZWarden.Web has no liveness endpoint; F16's health model is
authenticated and PZ-server-shaped, unfit for a container probe. Third, the chiselled .NET runtime images
carry no shell or `curl`, so a Compose healthcheck needs a probe tool present in the image.

## Decision

- **Layout.** `deploy/compose/` holds `compose.yaml` (base), `compose.postgres.yaml` (overlay, PR-B),
  `.env.example`, `.gitignore` (ignores `.env`), and `bootstrap-secrets.{sh,ps1}`. New multi-stage Dockerfiles
  live at `src/ZWarden.Web/Dockerfile` and `src/ZWarden.Agent/Dockerfile`; both build from the repository root
  context, run **non-root** (uid 10001), and use Debian-based runtime images (`aspnet`/`runtime`) so the Web
  image can carry `curl` for its healthcheck. F12's PZServer image and F32's Caddyfile are reused unchanged.
- **Two DB modes.** Base = SQLite at `Data Source=/data/zwarden.db` on a named volume, `ZWarden__Database__Provider=sqlite`.
  Postgres mode = `docker compose -f compose.yaml -f compose.postgres.yaml up -d`; the overlay adds the
  `postgres` service (+ volume, `pg_isready` healthcheck) and overrides only Web's provider + connection string.
- **Topology & hardening.** Two networks: `frontend` (Caddy ↔ Web, Agent → Caddy) and `docker-proxy`
  (`internal: true`, subnet `172.31.0.0/24`, Agent → wollomatic only). Only Caddy publishes ports (80/443).
  wollomatic carries the **same GET/HEAD/POST/bindmount allowlist the F13 drift tests enforce, verbatim**, with
  `-allowfrom` scoped to the internal subnet (a prod tightening over the dev graph's `0.0.0.0/0`). A Caddy
  network alias makes `wss://${ZWARDEN_DOMAIN}` resolve to Caddy inside the stack.
- **Secrets & enrollment.** `bootstrap-secrets.{sh,ps1}` generates the key ring and DB password into a
  git-ignored `.env` and refuses to overwrite an existing one. Enrollment is operator-driven: bring up
  Caddy+Web, run the First-Run wizard, paste its one-time secret into `.env`, start the Agent — which enrols
  once and persists its per-Agent credential on a named volume (F9).
- **Liveness & ordering.** ZWarden.Web gains an unauthenticated, DB-free `GET /healthz` (allow-listed past the
  first-run gate) used as the container healthcheck; Caddy and the Agent `depend_on` Web `service_healthy`.

## Alternatives considered

- **Reuse the Aspire graph / `dotnet publish`-generated Compose.** Rejected: ADR 0031 fences Aspire to
  dev/test; production wants pinned, non-root, hand-authored artifacts, not a dev orchestrator's output.
- **Compose profiles for the DB modes.** Rejected: a profile can add the `postgres` service but cannot
  conditionally swap Web's provider env, so it still needs a second env source — the overlay file is the honest
  single-command mechanism. Two full separate Compose files were rejected for drift.
- **Docker `secrets` from day one.** Rejected as the default (kept as the documented hardening upgrade):
  heavier (file mounts, `*_FILE` app support) than a single-node self-hosted install needs; the `.env` exposure
  via `docker inspect` is documented.
- **Auto-seed a shared enrollment secret (as the dev graph does).** Rejected: resurrects the dev-only shortcut
  the D-ENROLL guard forbids outside Development and weakens F9/PRD 63A single-use enrollment.
- **Relax the Agent validator to allow `http://web:8080`.** Rejected: weakens F8's fail-closed scheme rule; the
  Caddy-alias + wss path keeps production honest.
- **Reuse F16 health for the container probe.** Rejected: authenticated, PZ-server-shaped, DB-touching — wrong
  for a liveness check.

## Consequences

- **Chiselled-image minimalism is traded for operability.** The Web image carries `curl` (a small bloat) so
  the Compose healthcheck works without a shell. Accepted deliberately for a reference deployment.
- **Private (`tls internal`) mode requires trusting Caddy's CA in the Agent container** for the co-located
  wss connection — exactly the step F32's `Caddyfile.internal` already calls out; the deployment guide gives
  the concrete mount. Public mode works out of the box.
- **The wollomatic allowlist now lives in two places** (the Compose command and the F13 tests). An offline
  drift guard (`ComposeDistributionTests`) asserts the Compose copy verbatim, so the two cannot silently
  diverge — but an intentional change must edit both.
- **PZ world data bind-mounts under `/tmp`** because the proxy's `-allowbindmountfrom` is `/tmp` (ADR 0008);
  operators wanting persistent PZ data on another path is a future allowlist decision, not F34's.
- **The reference is single-node.** Remote/multi-host agents are F35 (#54); this stack is the control plane
  they enrol against.
